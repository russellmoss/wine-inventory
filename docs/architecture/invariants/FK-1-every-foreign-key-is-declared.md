# FK-1 — every foreign key is declared somewhere machine-readable

> [!warning] Invariant (high, app-code + db-constraint)
> Every reference column in `schema.prisma` is declared as EXACTLY one of: a Prisma `@relation`, a composite constraint in `prisma/fk-registry.json`, or an explicit soft reference with a stated reason. A reference column that is none of those is a dangling pointer nothing checks. The registry is generated by replaying the migration history and is proven against `pg_constraint` on a real database, so the two derivations must agree.

**Guarded by:** `npm run verify:fk-registry` (static) **+** `npm run verify:fk-registry-db` (runtime, CI job `db-proofs`)
**Decision:** Data-layer review 2026-08-05 — see [[INVARIANTS]], [[data-model]], [[TENANT-1-rls-isolation]].
**Applies to:** `prisma/schema.prisma`, `prisma/migrations/`, `prisma/fk-registry.json`

## Why this exists

Cross-tenant-risk foreign keys are composite — `(tenantId, refId) → (tenantId, id)` — which makes a
reference across tenants **structurally impossible at the database**. That property is worth keeping.
The cost is that **Prisma cannot express it**, so those FKs are hand-written in migration SQL and 42% of
models (79 of 188) carry reference columns with no `@relation`.

The consequence, before this guard: **291 composite constraints existed only as lines inside 186
migration files.** Nothing verified that a new `*Id` column ever got its constraint written, or that a
dropped one was noticed. A new table could ship with a dangling reference column and the entire suite
would pass. `prisma migrate diff` is documented broken on this schema, so it could not close the gap either.

## The three-part proof

1. **`gen:fk-registry`** replays every migration in order, tracking FK `ADD` and `DROP`, and emits the
   FINAL state to `prisma/fk-registry.json` (435 constraints: 337 composite, 98 simple). Replay is not
   defensive — the first run applied **20 drops**, so collecting additions alone would have let stale
   definitions win.
2. **`verify:fk-registry`** (static, every PR) — each reference column in the schema is covered by a
   relation, the registry, or a documented soft reference.
3. **`verify:fk-registry-db`** (CI, real database) — the registry matches `pg_constraint` exactly,
   including **column order**: `(tenantId, lotId)` and `(lotId, tenantId)` are different constraints with
   the same members. This is the part that catches a parser bug, since the parse is the weak link.

The runtime proof deliberately does **not** auto-rewrite the registry on mismatch. Adopting whatever the
database says would convert a detected drift into a laundered one; a difference means the parser, a
migration, or the database is wrong, and which one matters.

## Soft references — a foreign key is sometimes impossible, not merely absent

Three categories are unconstrained on purpose, and naming them is half the value:

- **Actor snapshots** (`createdById`, `enteredById`, `actorUserId`, …) point at the **GLOBAL `user`**
  table. A composite `(tenantId, userId)` FK is *impossible* — `user` carries no `tenantId` — and a
  simple FK would make an account undeletable while any history mentions it. Each is paired with an
  email snapshot so the record survives deletion.
- **External identifiers** issued by QuickBooks, Commerce7, GitHub, Copernicus, NOAA, RCC-ACIS. No local row.
- **Correlation keys** (`transferGroupId`, `batchId`, `runId`) group sibling rows; they point at nothing.

⚠️ `locationId` is listed **per column**, not by name, because it is a genuine composite FK on
`cellar_material` and `supply_lot` while being a documented plain ref on four other tables. A name-based
exemption would have silently excused the real ones.

## The shrink-only baseline

`prisma/fk-baseline.json` holds **85** reference columns that predate the guard. Each is a pending
decision, not an accepted state: write the missing constraint, or move it to a soft-reference category
with the reason. **Never add to it** — the guard fails on a stale entry too, so the ratchet can only
tighten. Triage groups are in [[data-model]].

The one group needing a product decision rather than a mechanical fix: `Lot.originVineyardId` /
`originBlockId` / `originSubblockId` / `originVarietyId`. Either those are constraints that were
forgotten, or they are deliberate origin snapshots that must outlive a deleted vineyard. Given how
consistently this schema snapshots history, the latter is likely — but it is undocumented either way.
