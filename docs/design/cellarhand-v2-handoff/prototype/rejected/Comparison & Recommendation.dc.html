Three directions · one workflow

Comparison, decisions, recommendation

All three run the same slice — /work-orders → /[id] → /execute → recorded — on the same day at Demo Winery, with the same 25-PN-04 barrel-down. They differ in information architecture, hierarchy, density and interaction; the palette is nearly identical across all three on purpose, so the structural choices are what you're comparing.

Direction A
Warm operational editorial

The current identity, made operational. One reordered nav, comfortable density, type-led hierarchy. The lowest-risk evolution.

Direction B
Precision cellar system

Two apps under one brand: a stripped floor app and a dense manager console. Fastest for experts, most work to build.

Direction C
Modern AI-native winery

No sidebar. A Now surface ranked by consequence, a command bar for everything, writes previewed before they happen.

Dimension A · Warm operational B · Precision cellar C · AI-native
Information architecture One sidebar, regrouped as Today / The wine / The business. Same nav for everyone; admin items gated but present. Hard split by role. Floor app = 3 tabs. Console = rail + queue + workspace, no page loads between them. No persistent nav. Now is the front page; ⌘K reaches everything; a full directory sits behind one header button.
Triage model Four saved views + one "narrow by…". Buckets by urgency, each row with its own verb. A persistent scannable list column with sort chips. Selection updates the pane; the list never leaves. Ranked by consequence, not by due date, with the ranking's sources shown and the plain queue one click away.
Capture interaction One act per screen, field pre-filled from plan, ±nudge buttons, 56px primary that names the value and the next stop. Nine barrels = nine rows in one grid on desktop; a dedicated 64px keypad on the phone. Enter records, Tab advances. Voice or type fills the same form; the screen states the resulting ledger change before you commit it.
Density Comfortable. ~3 orders per screenful; 44px rows. High. ~12 orders and 9 capture rows on one console screen; 32px rows. Spacious head, dense tail — one large lead item, then compact rows.
Where AI lives A bylined column in the brief: observation, source chips, one draft action. Never covers content. A result type inside search, always below the record matches, plus one strip under the capture grid. Structural: it ranks Now, explains abnormalities, and drafts diffed writes in a dedicated review rail.
Production context Right column, three collapsible levels: stage bar, lineage timeline, next step. A six-cell fact strip under the title — stage, volume, chemistry, destination, progress. No graphic. A six-stage bar at the top of the brief; solid = recorded, hollow = planned. Same component on lots and vessels.
Best for Small-to-mid estate wineries where everyone does a bit of everything, and for selling the product. Larger wineries and custom-crush, with dedicated cellar crews and hundreds of barrels. Wineries whose bottleneck is judgement, not typing — and the strongest differentiated pitch.
Main risk Least differentiated. At 400 barrels the comfortable density becomes a lot of scrolling. Two shells to build and maintain, and role boundaries in a small winery are blurrier than the design assumes. Findability depends on a command bar and ranked surface. If ranking is ever wrong, trust drops hard.
Build cost from today Low. Component and nav work; no new architecture. High. New shell, new role model, virtualised lists, a keypad component. High. Command bar, ranking service, draft/diff model, provenance plumbing.

Decisions common to all three, and what they cost

Wine is no longer a status colour

The gold→wine drift didn't just mislabel a token; it made every task status identical on the busiest screen. Wine now means brand and "the one action to take". Status gets deep-blue / green / golden / red plus a glyph.

Cost: the brand colour appears less often, so the product looks marginally less "Cellarhand" at a glance. Worth it — a colour that means five things means nothing.

"Correct", never "Undo"

You told me the ledger amends rather than reverses, so the word is Correct everywhere, the receipt says the entry is permanent, and corrected entries stay visible with both values in the history. Rule 8's blocked case gets a named later operation and a "unwind the chain" path.

Cost: "Undo" is a friendlier word and reduces fear more. Accuracy wins: promising undo and delivering an amendment is the same class of defect as the offline label.

The connection state changes the verb

With a real queue coming, offline is a named state — Held — with a count, a list of what's held, the sentence "not on the server yet", and a primary button that reads Hold instead of Record. The word on the button is the contract.

Cost: the interface visibly changes under the user mid-task, which is normally something to avoid. Here the change is the information.

The plan is the default value, not a separate mode

Deleting the Edit gate removes two clicks per task — ~24 on a twelve-task morning — and removes a mode named after the exception.

Cost: an editable field is easier to change by accident than a read-only summary. Mitigated by naming the value in the button ("Record 225 L and go to B-117") and by correction being available after.

AI proposes; a person commits

Every AI write is a draft with a visible diff, the records it reasoned from, and an explicit confirm. Recommendation / draft / confirmed / completed are four distinguishable states, and only the last two exist on the server. No sparkles, no permanent chat panel.

Cost: slower than letting the assistant act. Correct for a system of record that feeds a TTB filing.

Filters shrink; saved views replace them

Seven fields and a scrolling vessel picker became four named views plus one expandable "narrow by…". Work is visible in the first screenful on both desktop and phone.

Cost: the power-user who filters by template and location and date now takes one extra click. Measured against every user paying 450px of chrome on every visit, that trade is easy.

Recommendation

Build A's shell. Ship B's capture. Add C's command bar — in that order.

If forced to pick one whole direction: A. It is the only one that reaches the floor this season, it preserves the identity that makes Cellarhand look unlike winery software, and it fixes every safety defect in the audit without a new architecture. B and C both bet the slice on infrastructure you'd be building at the same time as the redesign.

But the honest answer is that the three are not really rivals — they are three layers of the same product, and their best parts don't conflict.

Now — this harvest
A's shell, status ramp and execute flow

Reordered nav, the five-tone status ramp, the Edit gate deleted, honest connection states, correction on the act. Mostly component-layer work; every audit critical is closed.

Next — before next harvest
B's multi-row capture grid and floor mode

The nine-rows-in-one-table pattern is the highest-leverage thing in the whole exploration for a winery with real barrel counts, and it transfers straight to /bulk — the audit's runner-up slice. Ship "floor mode" as a preference, not a second app.

Then — the differentiator
C's command bar, draft-diff writes and Now

The command bar should land early regardless — it's the fix for S5 and it takes the Assistant off the critical path for findability. Now should replace the dashboard only once the floor loop has defined what "needs me today" actually means. That sequencing is the audit's own §8 argument, and I think it's right.

What I'd need to resolve before this becomes a build plan

1Which acts are correctable, and for how long. The designs assume value corrections are open until a later operation consumes the wine. If there's a time or approval boundary, the receipt copy changes.
2The 11 orphaned routes. I've assumed the review queue and templates belong under Work orders, and weigh-tags under Fruit intake — but that's a product decision, not a design one.
3Whether Setup and Audit log stay ungated. A and C show them to everyone as today; B hides them from the floor role. Audit §9 Q1 is still open.
4Real barrel and tank counts across target tenants. The density choice between A and B turns almost entirely on this number, and I've been guessing at it.
5Scanning. The audit notes no barcode support anywhere. Every one of these designs would get materially faster with a scan on the vessel — it's the single biggest unexplored win, and it needs a hardware answer first.
